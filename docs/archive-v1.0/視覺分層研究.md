# Lunar Lens：低頻重量與聲音分層研究

調查日期：2026-09-09。對照版本：Lunar Lens v0.1.0。

**歷史研究文件**：以下記錄 0.1 的診斷與當時提案；四層事件、八頻段、獨立包絡、低頻光量保留和新的構圖已在 1.0 實作。文中的舊行號及「尚未實作」描述只適用研究當時。現況以工程設計.md 和驗證紀錄.md 為準。

這次完成官方文件、公開原始碼與目前專案的對照。以下「已確認」是程式與文件證據；「建議」是下一版的設計判斷，尚未經實機視聽比較。本次只新增此研究文件，沒有修改演出程式或重新封裝版本。

目前最需要改善的是聲音與形體之間的分工：低頻應有可感知的體積、位移與回復力；各層應有自己的起音和消退。增加分析指標的數量，本身不會帶來這些效果。

## 目前程式的直接原因

| 已確認的實作 | 對觀看效果的影響判斷 |
| --- | --- |
| `code/lens_visual.js:35`：低頻從 0 到 1，軌道半徑只增加 0.7 格；立體聲寬度也能增加 0.7 格。 | 低頻的空間變化小，且與寬度共用同一個視覺變量，重量感不容易辨識。低頻也影響亮度與旋轉，但沒有專屬衝擊動作。 |
| `code/lens_visual.js:18–19,38`：手動選擇波浪、星點或極簡時，軌道的權重逐漸趨近 0。 | 低頻的主要形體會隨場景淡出。場景切換改變了聲音角色的可見性。 |
| `code/lens_features.js:24,29–36`：三頻段均使用 80 ms 平滑；各頻段的正向能量變化合成一個起音事件。 | 鼓擊、低音換音、高頻點擊容易進入同一條事件通道。這裡尚未分析完整頻譜的 spectral flux。 |
| `code/lens_visual.js:20–25,45,52–53`：合併後的起音產生同類粒子；全部圖層共用最終拖尾。 | 即使訊號數值不同，動作語彙與時間尺度仍相似；高頻短音可能看起來像持續的漂浮物。 |
| `code/lens_visual.js:39`：估算 pulse 只影響軌道上的小光點。 | 節奏沒有形成整個構圖的壓縮、推動或回彈。 |
| `code/lens_visual.js:58–60`：所有圖層相加後共同套用總亮度上限。 | 限光有助留白，但沒有低頻角色優先權；其他圖層變亮時可能連帶壓低低頻。 |
| `code/lens_analysis.genexpr:6–14`：160 Hz／2 kHz 的一階濾波分成三段，分段互有重疊。 | 這是頻段能量分析，沒有分離鼓、貝斯、人聲或伴奏。 |

先前正弦波與節奏測試可證明「分析值會正確變化」，無法證明「看得出音樂中哪個角色在變化」。使用者的回饋指出了後者的缺口。

## 值得採用的參考

### AudioLink：把聲音變化做成空間運動

官方文件提供 bass、low-mid、high-mid、treble 四段資料，以及時間歷史、多級平滑和累積能量控制的運動時間（Chronotensity）。它把即時反應、緩慢反應與持續運動分開供視覺使用。[AudioLink 文件](https://github.com/llealloo/audiolink/blob/master/Docs/README.md)

其 ReactiveFloor 範例依距離讀取不同時間的低頻歷史，使聲音反應沿空間傳播。這比所有位置同時閃亮更適合 Lunar Lens 的空間感。[ReactiveFloor 原始碼](https://github.com/llealloo/audiolink/blob/master/AudioLinkSandboxUnityProject/Assets/AudioLinkSandbox/Shaders/ReactiveFloorAudioLink.shader)

建議借用：低頻事件沿有限格距傳播；各層保留自己的歷史；持續聲音控制流動，瞬態控制衝擊。AudioLink 是 Unity／VRChat 等環境的參考，不能直接當成 Max 原生物件，也沒有提供樂器分軌。

### MilkDrop／Butterchurn：把衝擊與持續量分開

MilkDrop 同時提供即時與平滑後的各頻段能量，作者指南明確以兩者的比值示範辨識低頻突增；縮放、旋轉和位移都是可由聲音驅動的參數。[MilkDrop 作者指南](https://www.geisswerks.com/hosted/milkdrop2/milkdrop_preset_authoring.html)

Butterchurn 的實作為各頻段分別保留即時值、短期平均與長期平均，以該頻段自己的歷史做相對強度計算。[Butterchurn 音訊分析原始碼](https://github.com/jberg/butterchurn/blob/master/src/audio/audioLevels.js)

建議借用：低頻持續量控制形體大小，短期突增控制一次回彈；既保留相對變化，也保留絕對音量門檻，避免安靜樂段被自動增益放大成高潮。視覺外觀仍使用月光與暗部，不照搬其預設風格。

### WLED：有限 LED 數量下的幾何與包絡

WLED 的音訊模組具有 16 段 FFT 資料、頻率響應補償和快速上升／較慢下降的處理。其 Gravcenter 類效果會將音量映射成佔用的像素長度，並讓頂點按回落規則移動。[音訊模組](https://github.com/wled/WLED/blob/main/usermods/audioreactive/audio_reactive.cpp)、[Gravcenter 等效果原始碼](https://github.com/wled/WLED/blob/main/wled00/FX.cpp)

建議借用：讓音量決定清楚的格數、面積、邊界位置，再設計回落。注意 Gravcenter 在這份程式中讀的是總音量，不能把它說成已有低頻專用或樂器分離效果。對 8×8 而言，可辨識的幾何比微小形變更值得優先驗證。

### FluCoMa HPSS：把打擊性與持續性成分分開分析

HPSS 利用頻譜隨時間呈現的不同形態，分出打擊性與諧波性成分；官方示例中的吉他掃弦，也會把起音與延續部分分開。這能改善後續起音或音高分析，並不等於分出「鼓」與「其他樂器」。[HPSS 原理及聲音示例](https://learn.flucoma.org/reference/hpss/)

Max 的 `fluid.hpss~` 範例包含延遲查詢；增加諧波時間濾波長度也會增加延遲。[官方 Max 範例](https://github.com/flucoma/flucoma-max/blob/main/help/fluid.hpss~.maxhelp)

建議借用：持續低頻與低頻打擊分別驅動「本體」和「推力」。若加入 FluCoMa，需要額外安裝 Max 套件，並實測和對齊分析延遲。它不能可靠地告訴畫面「這裡是人聲」「這裡是鋼琴」。

### Demucs：真正接近樂器角色的分軌路線

Demucs 提供鼓、貝斯、人聲、其他伴奏的分離模型。原 Meta 倉庫已封存，作者也說明後續分支只處理重要修正，因此適合作為方法與對照基準，實際整合前仍需選定維護方式並驗證本機效能。[Demucs 官方說明](https://github.com/facebookresearch/demucs)

若目標是讓人聲、鼓與貝斯各有獨立視覺，這類方法比增加 FFT 頻段更貼近目標。可以對每首匯入的音檔使用完全相同的預處理，再把分軌只用於分析；實際播放保留原始錄音，分離產生的聲音瑕疵不必進入聽覺輸出。代價是首次分析等待、模型依賴與分離誤差，不能直接承諾任意現場輸入都能即時達到同樣效果。

### 回看 Lineform

檢查到的 `RandomTubes` 會把平均頻譜值、RMS 和波形振幅範圍映射到數量、粗細、速度與分布；`getAdvancedAudioInfo` 則計算整段音檔的基本統計。這些部分能啟發多維形態控制，但不能作為已完成分聲部識別的證據。[RandomTubes](https://github.com/Mizimo/Lineform-See-the-music/blob/main/src/features/visualizer/components/RandomTubes.jsx)、[音檔統計](https://github.com/Mizimo/Lineform-See-the-music/blob/main/src/lib/getAdvancedAudioInfo.js)

## 建議的下一版：四個同時存在的聲音角色

我建議先建立以下視覺分工，解決目前已有訊號卻看不清差別的問題。以下是原創設計提案；時間與尺寸是待比較的初值，不是已驗證的最佳值。

| 聲音角色 | 畫面上的動作 | 起音與消退 |
| --- | --- | --- |
| 低頻衝擊 | 月體或構圖中心短促收緊，再推開一圈輪廓；有約 1–2 格可見位移，保留黑色中心或外圍。 | 事件到達時快速出現，約 150–300 ms 回彈；從實際低頻瞬態觸發。 |
| 持續低音 | 有連續輪廓與厚度的低位弧／月體，音的延續能被看見；不隨場景消失。 | 跟隨持續能量，釋放比高頻長；不能每一幀都重新觸發衝擊。 |
| 中頻持續聲音 | 一條有方向、連續移動的月光線，跟隨聲音的延續、停頓及強弱。 | 平穩起伏；低可信度時不把頻譜變化畫成假旋律音高。 |
| 高頻細節 | 外圍稀疏、位置清楚的小星點或短線，帶出細碎節奏。 | 快速起音、約 60–140 ms 短消退；與低頻回彈分用包絡。 |

圖層始終保留固定職責，聲音沒有出現時可以自然退暗；不同場景只改構圖。低頻的空間位置、面積、包絡與高頻星點均有區別，顏色只作補充。

分析側保留每段自己的瞬態與持續量，使用更細的頻帶觀察低音分布；多個瞬態不再合成唯一粒子事件。必要時比較 HPSS 是否真的改善交疊聲音。未使用樂器分離之前，UI 應稱「低頻衝擊／持續低音／中頻／高頻」，不能標成確定的鼓、貝斯、人聲。

亮度分配先保留主要輪廓，再分配細節。低頻的重量主要來自佔用空間與回彈，不靠全屏白閃；總亮度控制仍保留。Launchpad 按壓可以沿用拉動中心、改變傳播與壓力反饋，並確保手勢不把所有音訊層都混成同一種光點。

統一邏輯適用於所有歌曲。音檔名稱、歌詞、固定段落時間、人工提示點均不參與渲染。即使之後採用分軌，也是每首歌相同的自動處理與映射。分析延遲的技術對齊不等於逐曲編排提示點。

## 驗證方式

1. 用分開的低頻脈衝、持續低音、中頻長音、高頻短音及它們的混合，觀察是否能辨識四種動作；灰階比較也要有區別。
2. 固定其餘輸入，只增加或移除低頻：主要輪廓應有明確變化，高頻細節不能把它擠掉。各場景都做同樣比較。
3. 用具有已知獨立音軌的材料，先逐層聽看，再混合聽看；特別比較底鼓與貝斯同時存在、人聲帶齒音、鋼琴強起音等交疊情況。
4. 跨不同音樂風格、音量與編制測試相同參數；安靜段落不能被自動增益變成高能量畫面。
5. 實機量測起音到 LED 的延遲，檢查短事件有沒有在 20 Hz 畫面更新間遺失；先保留事件並調整包絡，再判斷是否需要提高更新率。
6. 最後做原音播放的主觀比較：觀眾能否指出低音進入、衝擊發生、持續聲部停下與高頻細節出現。RGB 合法、數值正確或測試通過都不能代替這一步。

優先順序是視覺角色與獨立時間尺度，其次是 HPSS 的效果／延遲比較；需要明確樂器身份時，再把統一的分軌分析作為架構升級。當前研究沒有證明任何新方案已達到主觀效果，也沒有進行新的硬體視聽驗證。
